# Product Requirements Document — Real-Time Trilingual Translator

**Версия:** 1.0  
**Дата:** 2025-10-19  
**Автор:** Codex (GPT-5)  
**Принципы:** OpenAI-First, минимализм кода, прозрачность метрик, скорость запуска

---

## 1. Цели продукта
- **Предоставить** мгновенный потоковый перевод между русским, английским и немецким языками с минимальной задержкой и высокой точностью.
- **Подтвердить** ценность OpenAI-First подхода: собственный код ограничивается auth, оркестрацией и наблюдаемостью; интеллектуальная работа выполняется OpenAI Responses/Realtime API.
- **Обеспечить** прозрачность и управляемость: метрики, rate limiting, строгие политики безопасности и готовность к масштабированию.

### Ключевые KPI
| Метрика | Целевое значение | Описание |
|---------|------------------|----------|
| First-token latency | ≤ 800 мс | Время от запроса до первого токена в UI (95-й перцентиль) |
| Успешные переводы | ≥ 99% | Доля запросов, завершившихся без 5xx и 429 |
| Пропускная способность | ≥ 50 одновременных потоков | Количество параллельных SSE-сессий на инстанс |
| Стоимость | ≤ $0.002/1K токенов | Средняя стоимость перевода (включая OpenAI) |

## 2. Целевая аудитория и сценарии

### Персоны
1. **Лингвист-переводчик** — быстро проверяет перевод или использует подсказки во время синхронного общения. Ожидает точности и обратной связи в реальном времени.
2. **Операционист поддержки** — принимает обращение клиента, оперативно отвечает на иностранном языке. Требует доступность и простоту UI.
3. **Менеджер продукта** — интегрирует сервис в существующий B2B-инструмент. Нужны API, SLA и понятная документация.

### Основные сценарии
- **S1. Быстрый текстовый перевод:** Пользователь вводит текст (до 4К символов), получает потоковый перевод с меткой времени и указанием модели.
- **S2. Сохранение короткого контекста (MVP):** Перевод одного сообщения без хранения истории. (Расширение — хранение истории в сессии).
- **S3. Голосовой перевод (пост-MVP):** Пользователь запускает WebRTC-сессию, говорит на родном языке, слышит перевод в реальном времени и видит субтитры.
- **S4. Интеграция через REST:** Партнёр отправляет запрос `POST /translate` и получает результат с мета-данными.
- **S5. Мониторинг и поддержка:** DevOps/Support отслеживают `/metrics`, логируют ошибки и работают с rate limit.

## 3. Область действия (Scope)

### Must Have
- SSE-потоковый перевод для `ru/en/de`, автодетект исходного языка.
- JWT-аутентификация (HS256 → RS256), выдача токенов на 30 минут.
- Rate limiting per user (120 req/мин по умолчанию) с Redis в проде.
- Кэширование переводов с настраиваемым TTL.
- Метрики Prometheus: количество запросов, статус, latency, ошибки OpenAI.
- Документация: API, Setup, Security, Deployment.
- CI/CD: тесты, линтеры, build-скрипты Docker (минимальный pipeline).

### Nice to Have
- Реализация Realtime API (WebRTC) с эфемерными токенами.
- UI-показатели (first-token latency, пер-centile графики).
- Контролируемая история переводов на фронтенде.
- Облачный IaC (Terraform) и GitHub Actions pipeline.
- Модерация контента перед отправкой в OpenAI.

### Out of Scope
- Собственный ML или fine-tuning.
- Поддержка >3 языков в MVP.
- Сложные права доступа (RBAC, организации).
- Сохранение пользовательских данных в базе.
- Собственная аналитика интерфейса (веб-вью без внешних трекеров).

## 4. Функциональные требования

### 4.1 Фронтенд
- **FR1**: Получение JWT токена через `/auth/token` и хранение в state (только в памяти).
- **FR2**: Отправка текстовых запросов, получение SSE-ответа, правильная сборка chunk'ов с буферизацией незавершённых строк.
- **FR3**: UI для выбора целевого языка и отображения перевода; обработка ошибок (429, 401, 5xx).
- **FR4**: Показ вспомогательной информации — модель, статус стрима, задержки.
- **FR5 (пост-MVP)**: UI для старт/стоп голосовой сессии.

### 4.2 Backend
- **BR1**: Endpoint `POST /auth/token` выдаёт JWT с RS256, срок 30 минут, `kid` для вращения ключей.
- **BR2**: `POST /translate` и `POST /translate/stream` принимают `TranslationRequest`, проверяют лимиты, обращаются к OpenAI Responses (async), возвращают результат, учитывают кэш.
- **BR3**: Кэш реализуется через асинхронную обёртку; TTL читается из конфигурации. В проде — Redis; в dev — in-memory с очисткой.
- **BR4**: `POST /realtime/token` создаёт эфемерный токен OpenAI (как только функция станет активной).
- **BR5**: `/metrics` и `/healthz` доступны без auth; `/metrics` предоставляет Prometheus-compatible поток.
- **BR6**: Логирование ошибок и предупреждений с уровнем `INFO` по умолчанию, возможность переключения.

### 4.3 DevOps / Ops
- **DR1**: Dockerfile для backend/ frontend, проверенный `docker-compose` для локального запуска.
- **DR2**: Скрипты тестирования (`poetry run pytest`, `npm run lint`) и инструкции в `DEVELOPMENT.md`.
- **DR3**: Механизм для ротации JWT-ключей и OpenAI API ключей (описание + инструкции).
- **DR4**: Документированные шаги деплоя; в случае отсутствия CI — указано, что требуется ручной build/push.

## 5. Нефункциональные требования
- **Производительность:** 95% запросов < 800 мс до первого токена; пропускная способность ≥ 50 потоков/инстанс.
- **Надёжность:** Грейсфул деградация при rate limit OpenAI (retry + ошибка 429 для клиента).
- **Безопасность:** RS256 JWT, HTTPS, CORS с белым списком, ограничение размера тела запроса (например, 16 КБ).
- **Удобство поддержки:** Codebase ≤ 800 LoC на backend, ≤ 350 LoC на frontend (не включая генерируемый код). Понятная структура; линтеры поддерживают единый стиль.
- **Наблюдаемость:** Метрики + структурированные логи (JSON или стандартный формат); минимальный APM-хук для OpenAI (опционально).
- **Соответствие политикам OpenAI:** отсутствие запрещённого контента, корректная обработка ошибок API.

## 6. Зависимости и интеграции
- **OpenAI SDK** (Responses API, Realtime API).
- **Redis** (опционально) для rate limit и кэша в production.
- **Prometheus / Grafana** — для метрик.
- **Docker / Docker Compose** — локальный и production-орchestration.
- (Опционально) Terraform, GitHub Actions — если инфраструктура автоматизируется.

## 7. Риски и допущения
- **Лимиты OpenAI:** превышение квоты приведёт к ошибкам 429. Требуется мониторинг и план квот.
- **Сетевые задержки:** SSE чувствителен к нестабильному соединению; внедрить reconnect-логику и ручной retry.
- **Голосовой режим:** OpenAI Realtime API может быть в бете → нужно предусмотреть fallback и флаг включения.
- **Документация vs код:** нежелательно расхождение (как сейчас с Realtime); обязанность — синхронизировать.
- **Без операций хранения данных:** клиенты должны знать, что сервис не хранит историю сообщений; это и плюс, и ограничение.

## 8. Метрики успеха
- **Product/Usage:** MAU, количество переведённых символов, доля повторных сессий.
- **Quality:** Пользовательский NPS, % ручных исправлений (через обратную связь), частота жалоб.
- **Ops:** Среднее время между инцидентами (MTBI), среднее время восстановления (MTTR).
- **Cost:** Стоимость 1 перевода, прогноз бюджета (OpenAI cost dashboards).

## 9. План релизов

### Релиз 1 (MVP) — готовность к пилоту
- Async Responses API, SSE с корректным парсингом.
- JWT RS256, rate limiting, кэш с TTL.
- Документация (README, API, Security, Deployment), обновлённые `.env`.
- Метрики и healthcheck.

### Релиз 2 — Production Hardening
- Redis интеграция, circuit breaker, retry-политика.
- CI/CD pipeline (lint/test/build), базовая IaC/инструкции.
- Alerting для SLA (Prometheus rules).
- Улучшенный UI (latency, состояние перевода).

### Релиз 3 — Голосовой режим и расширения
- Realtime API, эфемерные токены, UI для Voice-to-Voice.
- Контроль качества (feedback UI, ручная корректировка).
- Дополнительные языки (флаг) при достаточной калибровке.
